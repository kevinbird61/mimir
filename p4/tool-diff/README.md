# Difference of tools

這個部份主要探討 "使用工具上的不同" 對於 Anomaly detection 的差異。探討方向主要為 "polling-based"、"push-based"。(**這部份主要可以跟 OF 版本的實作來比對，以及跟將 detection algorithm 直接嵌入到 P4 program 內的版本做效能比較。**)

| | Push | Pull |
| :--- | :--- | :--- |
| 設備初始檢測 | 網路設備啟動後馬上上傳註冊，讓 `監控系統` 馬上發現該裝置，確保監控的 `即時性`、和 `不間斷性` | 需要 `監控系統` **定期掃描** *地址* 來發現新的設備，掃描速度取決於 `地址段的大小`，以及 `掃描間隔` |
| Scalability 擴展性 | 上傳狀態數據這一個環節，交給了每一台網路設備，而監控系統僅僅是監聽發過來的更新數據、並儲存到其系統內。對於網路設備而言，只要有數據就馬上發送給監控端，而且無論網路設備端還是監控端，都不需要維持對話關係、皆為一次性傳輸。 | 監控系統的負載、和查詢客戶端數量 **成正比**，同時監控系統還需要為每一個查詢保持 communication，這樣才能匹配返回的查詢結果。被查詢的網路設備，需要臨時中斷其他任務來處理 `監控端發送來的` 查詢命令。 |
| 運維複雜度 | 簡單配置網路設備即可實現主動上傳數據的功能，相關防火牆需要開啟策略，運行網路設備傳輸數據到監控系統。這個與傳統查詢方式相反。 | 監控平台需要配置大量的設備列表，以及接入這些設備所需要的密碼、或者是 community，以及需要收集的數據類型等等。防火牆需要開放雙向通信、查詢和 trap。 |
| 數據精確度 | 高頻率傳輸，單向傳輸 | 長間隔時間、需保持通話，雙向傳輸 |
| 延遲 | 開銷低，實時（**Real-time**）性高 | 開銷高，實時性低 |
| Flexibility 靈活性 | 相對受限的靈活性，只能導出設備 `預定義的參數` | 靈活性高，可以導出任何 MIB 定義好的數據參數。 |

> 轉載自 `SNMP 以死`
> 
> **而在靈活性的部份，則可以看到在有了 P4 之後，Push-based 的方法上也應該能擁有相當好的靈活度**。

## Polling-based

* P4 + SNMP
  * 基於 SNMP 的設計下去做 P4 的版本。用 P4 架構來完成 polling-based 的情境。
  * 這個意義在於跟 **同為 P4 製作的其他版本做比較**，而非實現一個既有效率差的情境。

## Push-based

> 在 push-based 的情境上，還有一個比較新的技術名稱 - Streaming Telemetry，像是用 sFlow、OpenConfig 等工具實現。
> 而在研究了 NetFlow 的機制後，也是一個 push-based 的方法。
> 而 INT 的實現，則因歸類而放到了 sys-diff 當中。

* P4 + NetFlow
  * 這部份主要利用了 NetFlow 的設計，並將這個設計透過 P4 做開發，完成一套基於 BMv2 以及 python 版本的 P4Runtime controller/collector 做實現。
